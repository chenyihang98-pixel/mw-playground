# 关卡工坊怎么做的

写一句话就出一关。这篇讲背后哪些交给模型、哪些由程序来做，接着 [README](../README.zh.md) 里那张图往下说。

## 模型只写说明书

模型不写坐标。不卡进墙里、每颗宝石都走得到、守卫的巡逻路线走得通，这类几何上的事由程序来生成和检查更靠得住。交给模型的只有一件：把一句话换成有限的几个选项。

模型写的“关卡说明书”里只有这些：

| 项目 | 选项 |
|---|---|
| 地图大小 | 小 / 中 / 大 |
| 障碍多少 | 少 / 中 / 多 |
| 高台数量 | 0 到 4 |
| 宝石数量和放法 | 分散 / 靠边 / 只放在高台上 / 扎堆 |
| 守卫数量和巡逻方式 | 绕圈 / 来回 |
| 难度倾向 | 轻松 / 普通 / 紧张 |
| 外观 | 草地、沙地、雪地 × 白天、黄昏、夜晚 × 晴、雾、雨 |
| 出场人物 | 名册里的谁，当同伴还是守卫，各带一句台词 |
| 标题和开场白 | 自由写的短句 |

用 JSON Schema 让模型输出，拿到以后再用 zod 查一遍。多出来的字段一律不收，所以模型就算自己加上坐标或时间限制也进不来。

## Schema 管不到的规则

类型和范围 Schema 能管，组合起来的规则要另外查：

| 地图 | 宝石 | 守卫 |
|---|---|---|
| 小 | 2 到 5 颗 | 最多 1 个 |
| 中 | 3 到 7 颗 | 最多 2 个 |
| 大 | 4 到 9 颗 | 最多 3 个 |

- 宝石“只放在高台上”时，每个高台最多 2 颗
- 同伴最多 3 个
- 能出场的只有这次请求里勾选的人，分工也只能是允许的那几种

## 流程

LangGraph 的图一共六步（`server/graph.ts`）：

1. **读懂请求**：模型觉得需要时，会调用名册工具
2. **写说明书**：结构化输出
3. **检查**：类型和范围、组合规则、人物和分工
4. **生成布局并检查**：生成器按种子出结果，同一个种子每次都一样；检查器是另外写的一段程序
5. **预览**：停在这里，等玩家决定
6. **保存**：确认后从停下的地方继续，保存

## 不顺利的时候

按失败的种类分开处理：

- **说明书不合规则**：把哪一项、为什么不行告诉模型。说明书一共能写 3 次（第一次加两次修改）
- **放不下或太远**：程序先自己重试几次，再调整一次条件；还不行才交回模型
- **检查器不认生成器做出来的布局**：这是程序的毛病，不交给模型，直接报错
- **3 次都不行，或者超时**：换成内置关卡，并说明原因、和请求差在哪

## 预览和确认

预览那一步用 LangGraph 的 interrupt 停住，确认后用 `Command({ resume })` 接着跑。

- 确认时不调用模型，保存的就是预览里看到的那一份布局
- 连点两次确认，只保存一次
- 确认的结果还没回来时点了放弃或重来，之后迟到的结果直接丢掉
- 没确认的预览放在服务的内存里（MemorySaver），服务重启就没了，界面会提示重新生成

恢复的时候，带 interrupt 的那一步会从头再跑一遍，所以这一步在停下之前只做计算，不做别的。

## 名册工具

模型能调用的工具只有 `lookup_roster` 一个，只读。

- 调用后返回这次请求里勾选的人物（显示名和允许的分工），不按条件筛选
- 调不调用由模型自己决定
- 浏览器只发人物的 ID、显示名和允许的分工，不发模型文件

## 例子：退回修改

请求是“小地图，两个守卫，宝石越多越好”。

1. 第一次的说明书：`tier: small, guards: 2, collectibles: 5`
2. 检查没过。交回模型的原因是：“small 地图最多 1 个守卫，现在是 2：减少守卫，或换成更大的地图档位”
3. 第二次的说明书：`tier: medium, guards: 2, collectibles: 7`，检查通过，出预览

检查是过了，可请求里的“小地图”变成了中等地图。过规则和照着要求做是两回事，所以结果分开记。

## 例子：调用工具

请求是“让装甲女兵来当守卫，一个守卫就够了，中等大小的地图”。

1. 模型调用 `lookup_roster`
2. 工具返回“r1：装甲女兵，可以当同伴或守卫”
3. 模型在说明书里写 `cast: [{ personId: "r1", role: "guard" }]`、`guards: 1`
4. 服务把 `r1` 换回真正的人物 ID

名册的内容在写说明书的提示词里也有，所以光看“人选对了”说明不了它调用过工具。留下调用记录的就是这一次。

## 试过的 8 次

2026 年 11 月，Windows 11，RTX 5080（16 GB），Ollama 0.40.16，qwen3.5:9b-q4_K_M。

| 请求 | 结果 | 事先定的要求 | 用时 |
|---|---|---|---|
| 来一张小地图，四颗宝石分散在地面上，没有守卫。 | 一次通过 | 3 / 3 | 8.2 秒（含加载模型 5.9 秒） |
| 沙漠的黄昏，起雾，中等大小的地图。 | 一次通过 | 3 / 3 | 2.2 秒 |
| 让星璇当我的同伴，草地，白天。 | 一次通过 | 2 / 2 | 2.6 秒 |
| 让装甲女兵来当守卫，一个守卫就够了，中等大小的地图。 | 一次通过，调用了一次工具 | 3 / 3 | 3.3 秒 |
| 大地图，三个高台，宝石只放在高台上，一共六颗。 | 一次通过 | 3 / 3 | 2.2 秒 |
| 中等大小的地图，两个守卫来回巡逻，下雨的夜晚。 | 一次通过 | 3 / 3 | 2.3 秒 |
| 小地图，两个守卫，宝石越多越好。 | 改了一次后通过 | 不算（“小地图”没保住） | 3.7 秒 |
| 晴天的草地，小地图，三颗宝石放在地面上，没有守卫，让星璇跟着我。 | 一次通过 | 3 / 3 | 8.3 秒（含加载模型 4.2 秒） |

- 最后一次是从浏览器界面走的整条路：导入角色、生成、确认、玩到宝石收齐、刷新后关卡还在。游玩时的按键是脚本发的
- 8 次的预览和保存下来的布局都是同一份，确认只花 2 到 5 毫秒
- 有一次长时间没用之后，第一个请求花了将近 1 分钟。那之后加载模型和生成就分开计时了

每一次的请求、说明书和结果在 [evidence/workshop-20261116](evidence/workshop-20261116/)。

## 为什么用 LangGraph

普通函数也能写。用状态图是因为有两处要“回去”：不合规则时回到写说明书，预览停住、确认之后再从那里接着跑。代价是得弄清楚框架的规矩，比如恢复时那一步会从头重跑。

## 没做的

- 没确认的预览在服务重启后还留着
- 同时处理多个请求
- 名册工具按条件查找
- 接真的 OpenAI 兼容服务试一遍（只用假服务试过）

## 代码在哪

| 文件 | 内容 |
|---|---|
| `server/graph.ts` | 图本身，退回修改和换内置关卡也在这里 |
| `server/prompts.ts` | 提示词 |
| `server/workshop.ts` | 生成和确认的入口，以及加载模型 |
| `server/roster.ts` | 名册内容和分工检查 |
| `src/game/level/gen/brief.ts` | 说明书的 Schema 和组合规则 |
| `src/game/level/gen/generator.ts`、`checker.ts` | 布局的生成器和检查器 |
