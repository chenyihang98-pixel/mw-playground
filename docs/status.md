### 第 1 轮审查后的修改

Codex 第 1 轮审查（候选 abf8088）提出 3 项阻塞问题，都已修正（违反的都是要求 5）：

1. 容器损坏被当作检查成功：重复的 JSON 块、重复的 BIN 块、未按 4 字节对齐的块只记在“问题”里，退出码 0。现在凡是检查到的容器损坏都返回错误（退出码 1）：块长度不是 4 的倍数、重复的 JSON 块、重复或不在第二位的 BIN 块、头部声明长度小于实际长度（尾部多余字节）、BIN 块比 buffers[0].byteLength 短或长出 3 字节以上、buffers[0] 指向 BIN 块但没有 BIN 块。顺带把 JSON 块的 BOM、0 字节补齐，以及缺 asset / asset.version、版本不是 2.x 也改为错误（three r187 的 GLTFLoader 在缺 asset.version 时会直接出错）。规范允许的未知类型块仍只记在“问题”里。
2. 访问器按未经验证的 count 分配数组：count 为 2**50 时抛 RangeError，被当作内部错误。现在先按 JSON 声明的 bufferView / buffer 长度检查访问区间（外部 buffer 也能检查），再读数据；读取改成按需逐个读取，不再按 count 分配数组；没有 bufferView 的全零访问器只检查一个元素。三角面数用到的 count 也先经过同样的检查。
3. FLOAT 分量的 NaN / Infinity 没有检查：包围盒在 JSON 里变成 null 但仍标为已计算。现在读取时逐个检查有限性，受影响的指标（实际包围盒、实际时长、水平位移）写“未计算”和原因，并在“问题”里记一条；包围盒和位移的计算结果也检查是否溢出。

另外修了一处同类问题：动画时长原来用 `Math.max(...列表)`，通道数很多时（实测 30 万个）会超出调用栈而抛异常。

### 设计说明

- 碰撞是 2.5D 的：胶囊在 XZ 平面上是圆，盒子、高台、坡道是 XZ 矩形加顶面高度。脚底高度为 y 时，顶面高于 y + 余量的部分是墙（着地时余量 = 迈步高度，空中为 0）；坡道的顶面是线性的，高于某个高度的部分仍是一个矩形。坡道只有两个侧面是墙：圆心在坡道的横向范围内时坡道不挡（斜坡顶面是地面，不是墙）；圆心在坡道上时，所贴的高台在坡道高端那一侧也不挡。这两条判断用每一小段移动开始时的圆心，所以从侧面靠近时仍会先被侧面挡住。圆被推出墙时只去掉法向分量，所以能沿墙滑动；位移按半个半径分段，挤不进比直径窄的缝时停在原处。地图边界直接限制圆心。
- 支撑高度取圆心所在位置的最高顶面；走出高台边缘时圆心离开顶面就开始下落。
- 守卫沿路线（最后一点回到第一点）匀速循环，只在地面上走，不受玩家影响；关卡校验要求路线离所有实体至少一个胶囊半径。守卫与玩家的胶囊水平距离小于两个半径、竖直范围重叠就算接触。
- 胜负在同一步里先判收集再判时间；分出胜负、暂停、未开始时 `stepGame` 原样返回。重开就是重新生成关卡的初始状态（`restartGame` 的结果与 `createInitialState` 相等），界面上随后直接开始。
- 暂停时 `advance` 不推进并丢弃累计时间（继续时不会补上暂停期间的时间），同时释放指针锁定；连装饰性的动画（宝石旋转、待机呼吸）也停下。指针锁定时浏览器用 Esc 退出锁定，游戏把“游玩中丢失锁定”当作暂停；之后 400 毫秒内的 Esc 按键被忽略，避免暂停后马上又继续。
- 指针锁定请求失败（浏览器不支持、被拒绝、出错）时改用按住左键拖动转视角；方向键也能转视角。游玩中没有锁定时，点一下画面会重新请求锁定。游戏自己释放锁定（暂停、结束）和浏览器解除锁定（Esc）分开处理，暂停后马上继续不会被误判成又一次暂停。
- 视觉模型和物理胶囊分开：`CharacterView.root` 跟随胶囊脚底位置和朝向，模型挂在它下面的 `model-slot`。守卫用同款小人，换红黑配色。

### 规则

- 片段标识：稳定标识是“文件内容的 SHA-256 + 片段序号”；名字只用来显示（无名的显示为 `animation_<序号>`），同名片段靠序号区分。手动设置都按序号保存。
- 播放方式：读 `clip.userData.loop`。true / false 是明确值；缺失和非布尔值都算“未知”，按用途推断（待机、走、跑循环，其他只播一次），界面标“推断”。false 和缺失分开处理。跳的槽位总是只播一次。
- 用途识别：名字拆成词（按非字母数字分隔、拆开驼峰，不区分大小写）后按词首匹配英文关键词，中文按子串匹配。先看动作词（aim / fire / firing / shoot / reload / attack / punch / kick / hit / death / die / dance，以及瞄准、射击、开火、换弹、装弹、攻击、受击、死亡、跳舞），命中就归为“其他”；再依次看 jump / 跳 → run、sprint、jog / 奔跑、跑 → walk / 行走、走 → idle、stand / 待机、站立；都没有就是“其他”。
- 自动建议（每个动作槽位选一个）：
  1. 有手动把用途设为这一项的片段时，用其中序号最小的；
  2. 否则在“识别为这一用途、没有手动改成别的用途”的片段里选：待机、走、跑排除极短的片段和带位移（且没有锁定）的片段；优先 loop 明确为预期值的（待机、走、跑为 true，跳为 false），再按序号从小到大取第一个。其余候选在卡片上注明，可以手动选。
- 兜底：没有走用跑放慢（走速 / 跑速）；没有跑用走加快（跑速 / 走速）；没有待机用走（含由跑得到的走）的第一帧静止，也没有走就用绑定姿态；走和跑都没有（包括静态模型，以及只有节点动画、但用途都不是移动的模型）时提示“没有适用的移动动作，将使用整体摆动效果”，移动时让外层摆动节点里的模型整体上下晃动、向前倾。没有跳的片段时，跳跃中保持当前动作。
- 带位移的识别：
  1. 找片段里有 position 轨道、在层级里最靠上（离模型根最近）的节点；
  2. 能明确识别要同时满足：这一层只有一个这样的节点；它的父链（到模型根为止）在片段里没有旋转动画（也没有缩放动画，否则坐标系不确定）；父链到模型空间的静态变换可逆；
  3. 用轨道自己的插值器（与播放时一致）取这个节点的位置，换到模型空间，算相对第一个关键帧的水平（XZ）位移，最大值超过 0.2 m 就标为“带位移”。线性和阶跃插值只看关键帧（最大值一定在关键帧上）；CUBICSPLINE 在每个关键帧区间里再均匀取 31 个点，覆盖关键帧之间的运动。
- 锁定水平位移（每个片段单独勾选，只在能明确识别时提供）：生成一份片段副本，在模型空间里把这个节点每个关键帧的 X、Z 换成第一个关键帧的 X、Z，Y 保留；CUBICSPLINE 的切线去掉水平分量；其他所有轨道不变。原片段不改，取消勾选就用回原片段。不能识别时显示“该片段暂不支持锁定水平位移，请选择其他原地片段或使用兜底。”
- 归一化（只写外层节点）：包围盒按实际显示的顶点逐个计算（three 的 `getVertexPosition`：计入已经生效的 morph 权重，蒙皮网格再做蒙皮，含 bindMatrix / bindMatrixInverse 语义），实例化网格把每个 `instanceMatrix` 都算进去。带骨骼的模型按绑定姿态算（`src/import/bindPose.ts`）：绑定姿态由逆绑定矩阵（IBM）决定，文件里骨骼的初始姿态不一定是绑定姿态。three 显示蒙皮网格的方式与 glTF 规范一致（GLTFLoader 以单位矩阵绑定，attached 模式抵消网格节点自己的变换）：显示的顶点 = Σ w · K · v，K = 关节全局变换 · IBM。默认按 glTF 规范的场景空间：绑定姿态下 K = 单位矩阵，网格按原始顶点显示。兼容一种特殊导出：整个模型（蒙皮网格和骨架）被一起套进带变换的节点、IBM 没有跟着更新——真实资产 armored-soldier 就是这样，导出工具在原模型外面套了 −90° 旋转和 1.75 倍缩放两层节点，蒙皮网格和根骨骼都在里面。这时按网格节点空间理解（绑定姿态下 K = 蒙皮网格节点的全局变换 M）。只看文件的静态结构，同时满足才算：所有蒙皮网格节点的全局变换相同（M），M 不是单位矩阵、可逆，网格节点的父链里没有骨骼；每条骨骼链所在的普通父节点的全局变换也等于 M；文件里每个关节的静止姿态都正好满足 K = M（容差 1e-3，平移按骨骼分布的尺度换算；armored-soldier 的最大偏差约 5e-6）。其余一律按场景空间。判断与片段无关，增加、删除或修改动作都不会改变对同一套 IBM 的理解。然后按这种参照系算出每根骨骼的绑定本地变换（普通父节点的变换正确补偿），在临时克隆上摆好再量，量完丢掉克隆。绑定姿态在导入时只算一次，包围盒、“绑定姿态”片段和实例都用同一份。缩放到显示身高，最低点贴地，水平中心移到原点；绕 Y 轴按 90° 的倍数转。“没有待机也没有走”时的“绑定姿态”兜底用一个保持绑定姿态的片段（每根骨骼一组轨道），和其他动作一样淡入淡出；它的轨道路径和 GLTFLoader 给文件片段用的一致（有名字的骨骼用名字，无名骨骼用 UUID），three 按轨道路径给每个属性建一份混合状态，路径一致才能在同一份状态里交叉淡入淡出。
- 无名节点的轨道：GLTFLoader 用模板节点的 UUID 指定无名节点的轨道目标，克隆后 UUID 会变。每个实例为这类片段生成一份把目标改成自己节点 UUID 的副本（`ModelInstance.clipFor`），原片段不改；所有目标节点都有名字时直接用原片段。实例的结构是：模型槽 → 摆动节点 → 外层节点（归一化）→ 克隆的模型。
- 资源：模板场景只用来克隆，不播放、不加入场景。实例释放时只释放自己的骨骼和 mixer 缓存；几何、材质、贴图由资产统一释放（卡片关闭且没有实例在用时）。

### 存储格式和版本号

IndexedDB 数据库 `mw-playground`（数据库版本 1），对象仓库 `roster`，每个人物一条记录，键是文件内容的 SHA-256。记录（格式版本 1）：

| 字段 | 内容 |
|---|---|
| `format` | 固定为 `mw-roster-person` |
| `version` | 存储格式的版本号，现在是 1 |
| `id`、`sha256` | 文件内容的 SHA-256（十六进制，两者相同，也等于存储的键） |
| `fileName` | 原文件名 |
| `displayName` | 显示名（默认是文件名，最长 60 个字符） |
| `order` | 加入的先后（名册列表、守卫分配都按它排） |
| `role` | 分工：`player` 主角、`guard` 守卫、`playerGuard` 主角兼守卫、`companion` 同伴、`none` 不出场 |
| `settings.displayHeight` | 显示身高（米） |
| `settings.quarterTurns` | 绕 Y 轴转了几个 90°（0–3） |
| `settings.purposes` | 片段用途的手动选择，键是“SHA-256#片段序号” |
| `settings.playbacks` | 播放方式的手动选择（`loop` / `once`），键同上 |
| `settings.lockedMotion` | 勾选了锁定水平位移的片段（“SHA-256#片段序号”） |
| `file` | 原文件内容（Blob） |

- 只保存原文件和设置，不保存加载后的对象或归一化结果。
- 读出的每条记录都用 zod 校验。以下情况都不抛异常，提示后跳过那一项：
  - 版本号不是 1；
  - 格式名不对、字段缺失或类型不对；
  - 键和 id 不一致；
  - 片段键不属于这个文件。
- 跳过的项仍在名册里标为失败，只能删除，不会被覆盖。

### 恢复流程

1. 页面加载时读出所有记录。读不了（浏览器禁止、出错）时给出存储失败的提示，名册从空开始，游戏照常。
   记录读出来之前不能加入（提示“名册正在读取保存的人物，请稍后再加入”）：去重、上限和顺序都要按完整的名册算。读出来之后，还在恢复的项也已经在名册里，可以照常加入。
2. 校验每条记录（见上）。合格的按 `order` 排序，逐个处理：
   1. 把保存的文件内容交给 `importModel`，和导入新文件走同一条流程（类型、读取、预检、解析、加载后检查、归一化）。
   2. 新加载的资产的 SHA-256 必须等于记录里的值。
   3. 套上保存的设置：身高、转向、用途、播放方式、锁定。序号超出片段数或不能锁定的项忽略。
3. 某一项被拒绝或解析失败时，给出提示（“……恢复失败：原因，已跳过”），名册里标为失败，记录保留，可以删除；其余照常恢复。
4. 每恢复完一项就重新分配出场的人物。同一个文件和同样的设置，恢复后的尺寸、朝向、片段建议和手动设置与加入时一致（单元测试逐项比较；真实资产组也比较了尺寸和朝向）。
5. 加入名册之后，资产上的设置一变就保存。同一条记录的写入按顺序进行，失败时给出提示，不抛异常。

### 分工和分配规则（`src/roster/cast.ts`）

- 五种分工：主角；守卫；主角兼守卫；同伴；不出场。新加入的人物分工为“不出场”。
- 主角（含主角兼守卫）最多一个。设新主角或点“恢复默认主角”时，原来的主角（包括主角兼守卫）改为“不出场”。没有主角时用默认小人。
- 同伴最多 3 个（`ROSTER_LIMITS.maxCompanions`）：第 4 个设不上，给出提示。还在恢复、分工已经是同伴的人物也算在内。
- 守卫只替换关卡里守卫的外观，数量和路线不变：
  - 分工为守卫或主角兼守卫的人物按名册顺序（加入的先后），依次分给关卡数据里按顺序排列的守卫。
  - 人物不够时，剩下的守卫用默认小人。
  - 人物多出来时，多出的不出场，并提示“关卡里只有 N 个守卫：…… 不出场”。
- 主角兼守卫：主角和守卫的位置上各有一个独立的实例，两个实例的骨骼和 AnimationMixer 各自独立。
- 同屏实例上限沿用 P3 的 12（`IMPORT_LIMITS.instancesMax`）：
  - 按主角 → 守卫 → 同伴的顺序占用，主角兼守卫占两个。
  - 超出时，多出的守卫或同伴不出场，并提示。
- 恢复失败的人物不出场，并提示。
- 名册最多 20 个人物（`ROSTER_LIMITS.maxPeople`，包括恢复失败、仍留在存储里的项）。到了上限不能再加入，给出提示。
- 同一个文件（SHA-256 相同）再次加入时不新增，提示“已在名册里”，并在名册里标出那一项。“设为主角”遇到这种情况时，把名册里的那一项设为主角。
- 再次导入名册里已有的文件时，导入卡片打开名册里的那一份资产（刚加载的副本释放掉），在卡片上的修改会保存。
- 导入时名册里那一项还在恢复（或恢复失败）的，卡片上是另一份副本：
  - 这份副本上的修改不会被名册保存，所以卡片上的设置先禁用（身高、转向、用途、播放方式、锁定），并说明原因；
  - 恢复好之后卡片自动换成名册里的那一份，设置随之可用；
  - 点“加入为新人物”“设为主角”之前也会先换。
- 删除正在使用的人物：
  - 先从名册移除并重新分配：主角换回默认主角，守卫换回默认小人，同伴从场景和模拟里移除。
  - 再释放它的实例和资源（按 P3 的释放规则），最后从存储里删除。导入卡片上正打开着它时，一起关掉。
- 导入失败时，名册、分配和当前主角都不变。

### 同伴的参数（`SPEC.companion`）

| 参数 | 取值 | 说明 |
|---|---|---|
| 跟随距离 | 1.8 m | 目标点在主角身后这么远 |
| 左右间距 | 1.1 m | 多个同伴的目标点以主角身后为中心左右错开 |
| 停下距离 | 0.3 m | 离目标点不超过它就停下 |
| 重新起步距离 | 0.8 m | 停下后离目标点超过它才起步（避免抖动） |
| 跑步距离 | 4 m | 离目标点超过它用跑步速度（5 m/s），否则用走路速度（2.2 m/s） |
| 卡住距离 | 8 m | 离主角超过它…… |
| 卡住时长 | 3 s | ……并持续这么久，就传送到主角附近 |
| 重试间隔 | 0.5 s | 找不到可以传送的位置时，隔这么久再试 |
| 找位置的间距、圈数、方向数 | 1.8 m、3 圈、16 个 | 开局和传送时，先试这个同伴的跟随目标点，再在主角周围 1.8 / 3.6 / 5.4 m 的圈上，从身后开始左右交替找 |

（P6 起“跟随距离”和“左右间距”换成每个同伴各自的跟随位置 `SPEC.companion.follow`：左后、右后、更靠后的左后，见 P6 一节。）

`specProblems()` 增加了三条约束：

- 重新起步距离大于停下距离；
- 找位置的最大范围小于卡住距离；
- 跟随位置离主角的距离小于卡住距离。

### 同伴的设计说明

- 移动写在固定步长的纯模拟里，和主角用同一个 `stepPlayer`：同样的速度、迈步、坡道、重力、从边缘掉落、地图碰撞（障碍、高台侧面、边界）。同伴的输入是“朝目标点走”：
  - 方向指向目标点；离目标点远时跑，近时走；
  - 最后一小段按剩下的距离减速，正好停在目标点上；
  - 同伴不跳。
- 同伴和主角、其他同伴、守卫之间不做碰撞，可以重叠，所以不会推挡主角（单元测试：有同伴和没有同伴时，主角的每一步都完全相同）。
- 收集和守卫扣时只看主角，同伴不影响胜负；守卫的移动也不受同伴影响。
- 渲染层只读同伴的状态。
- 暂停、未开始、分出胜负时 `stepGame` 原样返回，同伴也停下。重开时同伴回到开局的位置。
- “能站的位置”同时满足：
  - 胶囊在地图内；
  - 脚下表面的高度和主角脚下表面相差不超过迈步高度；
  - 胶囊不和会挡住它的实体重叠（按迈步余量 0 判断，比移动时更严）。

  开局时找不到这样的位置，就和主角站在一起（可以重叠）；传送时找不到，就留在原地，隔 0.5 s 再试。
- 分工变化时同步模拟里的同伴（`setCompanions`）：
  - 还没开始时，所有同伴回到开局位置；
  - 否则已有的保留状态，新加入的出现在主角附近，移除的消失。
- 同伴是导入人物时，用 P3 的动画驱动按它自己的移动状态切换片段；静态模型用 P3 的整体摆动。

### 存储失败

- 以下情况都给出提示（名册面板顶部的红色提示，以及快照里的 `roster.storage.problem`）：
  - IndexedDB 打不开（浏览器不支持、被禁止）；
  - 配额不够（提示“存储空间不够”）；
  - 读写抛错、事务中止。
- 游戏照常运行，当前会话里的名册照常能用，只是不保存。之后某次保存成功时清掉提示。

### M2：inspect 报告里 translation 通道的水平位移改为模型空间

新口径（`src/asset/inspect/inspect.ts`，报告里写作“模型空间，XZ 平面，各关键帧相对首帧的最大水平距离”）：

- 取这个节点的父链（到场景根为止），用文件里的静态变换（`transform.ts` 的 `localMatrix` / `multiply`）把每个关键帧的位置换到模型空间。
- 取各关键帧相对第一个关键帧的水平（XZ）距离的最大值。报告还给出距离最大的是第几个关键帧、关键帧总数、首帧在模型空间里的 XZ。
- 关键帧之间不插值；CUBICSPLINE 只看关键帧的值（不看切线），报告里注明。
- 只算这个通道自身带来的位移：父链用文件里的静态变换，父链上其他节点的 translation 动画不计入，报告里注明。节点自己的 rotation / scale 不影响它的平移（平移在父节点的坐标系里）。
- 以下情况写“未计算”和原因，不填数字（不会把算不出的值填成 0）：
  - 父链在同一个动画里有 rotation 或 scale 通道，写“坐标系不确定”；
  - 节点有多个父节点或节点树成环（父链不确定）；
  - 数据读不出、有 NaN / Infinity、换算后溢出。
- 只有一个关键帧时位移为 0（已计算）。没有 bufferView 的访问器（按规范全为 0）只读不同的元素，不按声明的 count 逐个遍历。
- 耗时和节点数、通道数成正比：
  - 每个节点的静态全局变换只算一次，整个报告共用；
  - 每个动画只建一次“有 rotation / scale 通道的节点”的索引，每个节点父链上最近的这种节点也只算一次；
  - 两者都不用递归，很深的父链也不会爆栈。
- 和 P3 导入时的带位移识别（P3“规则”里“带位移的识别”）口径一致：都在模型空间，都相对第一个关键帧。不同之处只有一点：inspect 不在关键帧之间插值（P3 用轨道自己的插值器，CUBICSPLINE 在每个区间里再取样）。
- 报告的数据结构从 `{ from, to, distance }` 改为 `{ maxDistance, atKeyframe, keyframes, first }`，并增加 `interpolation`。

### 生成器（generatorVersion 1）

在 2 m 的粗网格上按顺序做：

1. 连通的可行走区域：
   - 最外一圈格子是通道；
   - 守卫的巡逻通道：loop 是一个矩形的一圈，back-and-forth 是一段 L 形；
   - 收集点和出生点的空地，各 3 × 3 格；
   - 几条通往随机锚点的通道。

   每块新挖的通道都用 L 形通道连到已有的通道上，所以整体连通。
2. 障碍和高台：
   - 高台占 2 × 2 格，坡道占高台一侧的 2 格，坡道低端外面那一格必须是通道；
   - 盒子只放在没被占用的格子里；
   - 盒子和高台离所在格子的边界至少 0.35 m。

   盒子高 0.6–2.4 m，坡道宽 1.1–1.3 m、长 2.6–3.6 m（不陡于 30°）。
3. 收集点、出生点和巡逻路线：
   - 收集点放在空地中央；clustered 放在同一块空地的各格，elevated 放在高台顶面（每个高台最多 2 个）。
   - 出生点放在出生点空地的中央。它离巡逻路线至少 5 m + 1 m（比检查器的要求多留 1 m），离收集点至少 4 m，朝向最近的收集点。
   - 巡逻路线沿巡逻通道的格子中心，只在地面上。back-and-forth 的路线点排成 A→K→Z→K（P2 的循环路线回到 A，就是来回各走一遍），守卫的运动规则不变。

其他规则：

- 随机数只来自种子（sfc32，种子用 cyrb128 散列）。每份说明书最多做 8 次布局尝试，第 k 次用子种子 `种子/attempt-k`。
- 全部放不下时返回“放不下：small 地图（24 m）试了 8 次都放不下这么多收集点、高台、守卫和障碍，可以减少数量或换成更大的地图档位”，并附上每次的具体原因。
- 检查没通过时直接返回 `rejected`（程序缺陷），不用别的子种子重试。

### 硬检查

对外只说“空间与规则检查通过，难度为估计”，不说“任何玩家都能在限时内通关”。检查器独立于生成器，只用布局、P2 的 schema / layoutProblems 和几何函数。检查项：

- 布局通过 parseLevel（结构和 layoutProblems）；
- 出生点的胶囊在地图内、不与障碍重叠；
- 收集点数量不少于目标数；
- 每个必需的收集点都能从出生点走到；
- 巡逻路线整段不穿过障碍（按守卫的胶囊半径算），只在地面上；
- 出生点离每个守卫的起点和路线至少 5 m（`GEN_CONFIG.check.spawnGuardDistance`）；
- 给了说明书时，布局和说明书一致：档位尺寸、高台数、收集点数、守卫数、elevated 的收集点都在高台上、back-and-forth 的路线来回对称。

失败原因是结构化的：每条带 `category`（`brief`：说明书或参数的问题；`layout`：检查发现的布局问题）、`code` 和说明。

寻路（保守）：

- 网格边长 0.25 m（`GEN_CONFIG.check.grid`）。
- 一个格子能站：格子中心离地图边界、离所有“墙”至少 R = 胶囊半径 0.35 m + 半个格子对角线（约 0.177 m）。相邻（8 邻接）的两个能站的格子之间走直线时，胶囊始终不碰墙。比胶囊直径窄的缝里没有能站的格子（实际要宽约 1.05 m 才算走得过）。
- 地面一层的墙是所有盒子、高台、坡道（不算迈上矮盒子，不算从侧面走上坡道）。每个高台一层，墙是除这个高台以外的所有实体。高台和地面不直接相连（不算跳上跳下）。
- 坡道只沿中线连接地面和高台：入口在低端外 R + h，出口在高端内 R + h。中线两侧各 R 宽的通道不能碰到别的实体，入口和出口的格子都要能站。按 P2 的碰撞规则，中线在坡道的横向范围内时坡道和它的高台都不挡，所以这条通道在模拟里一定能走。
- 收集点：某个能到达的格子中心，按那一层的脚底高度，收集点中心到胶囊轴线的距离不超过 0.8 m，就算能收集到。

### 难度估计和时间推算

这些系数、余量、上下限都是估计值，以后会按试玩结果调整；已保存的关卡不受影响（保存的是最终的时间限制）。

| 参数 | 取值 |
|---|---|
| 路线时间 T | 从出生点出发，每次去最近的（按检查器网格的路径长度）还没收集的必需收集点，按跑速 5 m/s 算。不求最优路线 |
| 难度系数 | relaxed 2.6、normal 2.0、tense 1.5 |
| 最低余量 | 20 s |
| 太远 | T × 1.5（三档里最小的）+ 20 > 档位上限：返回“太远”，进入调整或回退，不截到上限当作合理 |
| 时间限制 | 把（T × 本关系数 + 20）向上取整到秒，再限制在档位的上下限之间 |

程序调整：可选，最多一次，规则固定。调整后的说明书、原因和改了什么都记下来，然后重新生成（子种子 `种子/adjusted`）、重新检查。

- 放不下：障碍密度降一档；已经是 low 时，收集点数减到档位范围的下限。
- 太远：收集点数减到下限；已经是下限时不调整。

### 随机关卡、内置关卡、保存和重玩

- 随机关卡：
  - 随机说明书只产出合法的组合：elevated 只在高台够放下档位下限数量的收集点时才选；small 最多 2 个高台、medium 最多 3 个。
  - 出场人物从名册里现有的（已恢复的）人物中选，可以为空。
  - 一次“随机一关”最多尝试 3 份说明书（`GEN_CONFIG.random.briefs`），每份最多 8 次布局尝试 + 一次调整 + 8 次尝试，都是有限次。全部失败就加载回退关卡。
  - 检查器拒绝了生成器做出的布局（程序缺陷）时立即停止，不再换下一份说明书。界面写明“发现程序缺陷，已停止生成”和具体原因，控制台记一条错误，随后加载回退关卡，保证有一关可玩。
  - 取消（生成中“取消生成”，或预览时“放弃”）就结束这次生成，不加载回退关卡。
  - 根种子来自浏览器的 `crypto.getRandomValues`；生成器本身只用种子。
- 内置关卡：
  - P2 的 meadow、test-a、test-b 原样保留，视觉预设 grass / day / clear。启动时默认仍进入 meadow，`?level=` 照常可用，测试钩子的关卡列表不变。
  - 新增三关由生成器做出、冻结下来，以冻结的布局和规则为准（生成器版本变了也不重新生成）：

    | id | 标题 | 说明书 | 视觉 | T | 时间限制 |
    |---|---|---|---|---|---|
    | gen-1 | 晨光草地 | small、low、1 高台、3 收集点 scattered、1 守卫 back-and-forth、relaxed | grass / day / clear | 5.5 s | 35 s |
    | gen-2 | 沙丘黄昏 | medium、mid、2 高台、5 收集点 edge、2 守卫 loop、normal | sand / dusk / fog | 15.5 s | 51 s |
    | gen-3 | 雪夜高台 | large、mid、3 高台、6 收集点 elevated、2 守卫 back-and-forth、tense | snow / night / rain | 21.6 s | 60 s（截到下限） |

  - gen-1 同时是最终的回退关卡。
- 保存和重玩：
  - 已确认的关卡保存在 IndexedDB，与名册分库：数据库 `mw-playground-levels`，对象仓库 `levels`。键是布局哈希（规范 JSON 的 64 位 FNV-1a）。
  - 记录格式 `mw-saved-level`、版本 1，保存这些内容：
    - 规范化后的说明书和种子；
    - schemaVersion、generatorVersion；
    - 最终布局和视觉预设；
    - 最终生效的规则：时间限制、收集目标数、守卫扣时、冷却；
    - 来源：random、adjusted（程序调整过），以后还有 model；
    - 程序调整的记录。
  - 重玩时直接用保存的布局和规则，不重新生成，也不重算时间（加载模块不引用生成器和时间推算）。
  - 认不出的版本、损坏的记录、布局和规则不一致、哈希不对的记录，提示后跳过，列表里标出，可以删除。存储失败只给提示，本次会话里的列表照常可用。
  - 复现承诺：已保存关卡的布局和规则可以复现；不承诺不同浏览器上的物理过程逐帧一致。
- 关卡的出场人物：
  - 主角按名册。
  - 说明书列了出场人物时，这一关的同伴和守卫外观按说明书：同伴最多 3 个，守卫按列出的顺序分给关卡里的守卫，名册里的同伴、守卫分工这一关不用。没列时按名册的分工（P4）。

  - 开场白和台词显示在开始面板里。
  - 工坊生成的关卡见 F3。
- 视觉预设：
  - 主题改变地面、网格和盒子的颜色；
  - 时间改变天空颜色、环境光和太阳光的颜色和强度；
  - 天气 fog 是浓雾，rain 是淡雾加下落的雨滴，clear 没有雾。
  - 不做水面（地图边界照旧）。P6 再整理视觉。

### 未运行或未验证

- 随机测试只跑了有限次数（每个档位 200 个种子，加上若干固定样例），不能证明所有输入都能生成成功。“随机一关”在浏览器里的成功率只在端到端测试里用随机种子试过几次。
- 检查器的保守性来自构造上的论证（离墙至少 R、坡道只走中线通道），加上人工构造的布局和一个在模拟里实际走过的样例。没有对所有生成的关卡在模拟里实际走一遍。
- 时间限制的系数和余量没有经过试玩校准（任务说明里也注明是估计值）。不承诺任何玩家都能在限时内通关。
- 视觉预设只在无头 Chromium 的截图里看过，没有人工确认观感。没有在 Firefox、Safari 上验证 IndexedDB 保存关卡和预览画布。
- 不同浏览器上的物理过程是否逐帧一致没有验证，也不承诺。

### 已知问题和后续项

- 检查器的判定偏保守：不算迈上矮盒子、不算从侧面走上坡道的低处、要求缝至少宽约 1.05 m，所以有些实际能走的地方会判为走不到。生成器留的通道足够宽，固定种子集合里没有因此失败的。
- 时间限制常常截到档位下限（路线很短的小关卡）。系数和下限等试玩之后再调。
- 巡逻路线不避开收集点和坡道入口，守卫可能守在宝石旁边；难度只按路线时间估计，没有计入守卫。
- 生成在主线程上同步运行，“取消生成”只在两份说明书之间生效（每份通常只要几十毫秒）。
- 随机关卡的出场人物只从已恢复的名册人物中选；名册还在恢复时点“随机一关”，出场人物可能为空。

### 难度估计（关卡选择和开始面板上的标签）

## P8：关卡工坊（一句话 → 模型填说明书 → 程序生成并检查）

### 内容

- 本机服务（`server/`）：
  - 用 `node:http`，由已有的 `tsx` 运行，只监听 127.0.0.1（地址固定，不能配置），默认端口 8790（`MW_WORKSHOP_PORT`）；
  - 服务和 Vite 的代理用同一个规则取端口（`server/port.ts`）：环境变量优先，其次项目根目录的 `.env`；
  - 开发时由 Vite 把 `/api` 代理过去；
  - `npm run dev:workshop` 同时起 Vite 和服务。原来的 `npm run dev` 只起 Vite，工坊按“服务不可用”显示，游戏照常。
  - Playwright 的 webServer 同时起停 Vite 和服务（假模型模式）。
- LangGraph 流程（`server/graph.ts`），节点依次是：
  1. 理解请求：可以调用“查名册快照”工具，工具只读这次请求带来的快照；
  2. 写说明书：结构化输出，把 P5 说明书的 JSON Schema 交给模型；
  3. 校验：P5 的 `parseBrief`，加上快照里允许的分工；
  4. 生成布局并做硬检查：直接调用 P5 的 `produceLevel`，含有限次尝试和一次程序调整，不复制代码；
  5. 按类别处理失败；
  6. 预览（interrupt）；

### 设计要点

- 模型的输出只经结构化输出和 zod 校验进入流程。
  - 模型返回的其他内容一律不执行：“理解请求”这一步只执行“查名册快照”这一个只读工具，最多一轮，别的工具调用回一句“没有这个工具”。
  - 理解的结果只作为文字放进写说明书的提示。
- 名册快照：
  - 浏览器只发选中人物的人物 ID、显示名、允许的分工，不发模型文件。
  - 给模型看的时候每人一个代号（r1、r2…），服务把代号换回 ID 后再校验：
    - 人物必须在快照里（P5 的 `parseBrief`，rosterIds 就是快照）；
    - 分工必须是快照允许的（`roleProblems`）。
- 失败按 P5 流水线的结果类别处理，不另造一套：
  - 说明书错误：坏 JSON、schema、组合冲突、不存在的人物、不允许的分工。具体原因（人物 ID 换成代号）交回模型。
  - 放不下或太远：`produceLevel` 已经做过有限次尝试和一次程序调整，把它的说明（含调整了什么）交回模型。
  - 程序缺陷（检查器拒绝）：记一条错误日志，不交给模型，直接结束。浏览器回退，统计记为服务错误。
  - 模型写说明书一共最多 3 次（`MAX_BRIEF_ATTEMPTS`），用完还不行就回退。
  - P5 的检查规则没有改。
- 回退：
  - 加载 P5 的第 1 关（晨光草地，`FALLBACK_LEVEL_ID`）；
  - 说明来源（内置回退关卡）、原因、各次尝试的问题；
  - 和请求的主要差别：拿模型最后一次写出的合法说明书和回退关卡的说明书比；没有合法说明书时直接说明“不是按你的描述做的”。
- 中断与保存：
  - 生成和检查都在预览节点之前完成。
  - 预览节点在 `interrupt` 之前只调用纯函数 `previewOf(state)`，没有副作用。恢复时节点从头重新执行，结果相同。
  - 确认后进入保存节点，只返回状态里当前预览的那一份关卡（`final = level`）：不重新抽种子，不调用模型。
  - 服务端不存关卡：保存节点只“定稿”，返回布局、规则、说明书、种子、版本，来源记为 model，另附提供方和模型名。
  - 浏览器收到后用 P5 的 `SavedLevels.save` 写进 IndexedDB，存储格式不变（`source` 本来就预留了 model）。提供方和模型名不在存储格式里，所以只在预览和定稿的响应里显示，不保存。
- 检查点：
  - 只用会话内的内存检查点（MemorySaver），确认或放弃后删除，同时最多保留 16 个预览。
  - 每个服务进程有一个服务标识。确认时服务标识对不上（服务重启过）返回 `expired`，浏览器提示“工坊服务重启过，未确认的预览已失效”。
- 请求管理：
  - 生成标识由浏览器生成（UUID），发请求前就知道，取消时用它。
  - 浏览器只接受当前生成标识的响应，迟到的旧响应丢弃。
  - 确认按生成标识只发一次。服务端按生成标识只定稿一次，并发或重复确认返回同一份（`duplicate: true`）。浏览器按生成标识只写一次。
  - 取消：
    - 浏览器告诉服务取消，并中止这次请求；
    - 服务中止模型调用：每次调用新建模型对象，`fetch` 绑定这次调用的 AbortSignal；浏览器断开连接时也会取消；
    - 取消不算失败，不回退。
  - 超时：单次模型调用和整个请求都有超时（可配置），超时算服务错误，回退。
- 统计（`server/stats.ts`）：
  - 每个请求只记一条，记在生成结束时：出预览、回退、出错或取消。之后确认或放弃不再另记；“忙”或“不可用”被拒绝的请求不记。
  - 最终结果（六类）和原因分开存。另记提供方、模型名、修复次数、写说明书次数、模型调用次数、各阶段耗时（理解、写说明书、校验、生成、合计），以及玩家一句话的长度、快照人数。
  - 不记密钥、原文和人物信息。回退不算模型成功。
- 密钥：
  - 只在服务进程里使用；
  - 日志每一行先脱敏，错误信息只用固定说法（例如“模型服务返回错误（HTTP 401）”），不转发提供方的原文；
  - 健康检查只返回提供方和模型名；
  - 配置出错时只说哪个变量不对，不回显值；
  - 仓库和测试里只有一看就是假的 `fake-key-1`。
- 本机失败时不会自动切换到外部接口：提供方只由 `MW_LLM_PROVIDER` 决定。

### 第 1 轮审查后的修改

Codex 第 1 轮审查（候选 8cf4abe）提出 4 项阻塞问题，都已修正。

1. 要求 2：切换语言时没有等保存做完就刷新。
   - 名册的写入是排队进行的，已保存的关卡也是先改内存再异步写；改了设置马上切换语言，排队的写入可能丢掉。
   - 修改：
     - `src/i18n/lang.ts` 新增 `switchLangWith`：先等，再保存选择、刷新；
     - `src/i18n/browser.ts` 的 `switchLang` 用它，等的是 app 注册的 `setBeforeLangSwitch`；
     - `app.ts` 注册为名册和已保存关卡的 `whenIdle()`；
     - 等的时候语言选择禁用；写入失败（另有提示）也照样切换。
2. 要求 5：英语的分工选项在名册里被截断（下拉框被压窄，看不全 “Player character”“Not appearing”）。

   - 版面检查加了原生下拉框的检查：比它自然的宽度（容得下最长的选项）窄就算截断。加了这项检查以后，又发现导入卡片里片段的“播放”“用途”下拉框也被压窄，改成各占一行。
3. 要求 3：检查器的诊断信息在浏览器里仍是中文（例如“随机一关”缺陷说明里的具体问题）。
   - 修改：检查器的 22 条说明改成取词典，撤掉了源码扫描白名单里对 `checker.ts` 的整文件豁免。
   - P5 的独立性测试（`level-checker.test.ts`）允许的引用里加了 `../../../i18n`：i18n 只提供文字，检查器仍然不引用生成器（“不引用 ./generator”的断言没改）。
   - 服务端在 Node 里，检查器的说明照旧是中文。
4. 要求 1：`navigator.languages` 是空列表时，入口还会去看 `navigator.language`（例如 `ja-JP` 时按日语处理），和规定的“都没有时取 en”不一致。
