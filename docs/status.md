### 第 1 轮审查后的修改

Codex 第 1 轮审查（候选 abf8088）提出 3 项阻塞问题，都已修正（违反的都是要求 5）：

1. 容器损坏被当作检查成功：重复的 JSON 块、重复的 BIN 块、未按 4 字节对齐的块只记在“问题”里，退出码 0。现在凡是检查到的容器损坏都返回错误（退出码 1）：块长度不是 4 的倍数、重复的 JSON 块、重复或不在第二位的 BIN 块、头部声明长度小于实际长度（尾部多余字节）、BIN 块比 buffers[0].byteLength 短或长出 3 字节以上、buffers[0] 指向 BIN 块但没有 BIN 块。顺带把 JSON 块的 BOM、0 字节补齐，以及缺 asset / asset.version、版本不是 2.x 也改为错误（three r187 的 GLTFLoader 在缺 asset.version 时会直接出错）。规范允许的未知类型块仍只记在“问题”里。
2. 访问器按未经验证的 count 分配数组：count 为 2**50 时抛 RangeError，被当作内部错误。现在先按 JSON 声明的 bufferView / buffer 长度检查访问区间（外部 buffer 也能检查），再读数据；读取改成按需逐个读取，不再按 count 分配数组；没有 bufferView 的全零访问器只检查一个元素。三角面数用到的 count 也先经过同样的检查。
3. FLOAT 分量的 NaN / Infinity 没有检查：包围盒在 JSON 里变成 null 但仍标为已计算。现在读取时逐个检查有限性，受影响的指标（实际包围盒、实际时长、水平位移）写“未计算”和原因，并在“问题”里记一条；包围盒和位移的计算结果也检查是否溢出。

另外修了一处同类问题：动画时长原来用 `Math.max(...列表)`，通道数很多时（实测 30 万个）会超出调用栈而抛异常。

### 设计说明

- 碰撞是 2.5D 的：胶囊在 XZ 平面上是圆，盒子、高台、坡道是 XZ 矩形加顶面高度。脚底高度为 y 时，顶面高于 y + 余量的部分是墙（着地时余量 = 迈步高度，空中为 0）；坡道的顶面是线性的，高于某个高度的部分仍是一个矩形。坡道只有两个侧面是墙：圆心在坡道的横向范围内时坡道不挡（斜坡顶面是地面，不是墙）；圆心在坡道上时，所贴的高台在坡道高端那一侧也不挡。这两条判断用每一小段移动开始时的圆心，所以从侧面靠近时仍会先被侧面挡住。圆被推出墙时只去掉法向分量，所以能沿墙滑动；位移按半个半径分段，挤不进比直径窄的缝时停在原处。地图边界直接限制圆心。
- 支撑高度取圆心所在位置的最高顶面；走出高台边缘时圆心离开顶面就开始下落。
- 守卫沿路线（最后一点回到第一点）匀速循环，只在地面上走，不受玩家影响；关卡校验要求路线离所有实体至少一个胶囊半径。守卫与玩家的胶囊水平距离小于两个半径、竖直范围重叠就算接触。
- 胜负在同一步里先判收集再判时间；分出胜负、暂停、未开始时 `stepGame` 原样返回。重开就是重新生成关卡的初始状态（`restartGame` 的结果与 `createInitialState` 相等），界面上随后直接开始。
- 暂停时 `advance` 不推进并丢弃累计时间（继续时不会补上暂停期间的时间），同时释放指针锁定；连装饰性的动画（宝石旋转、待机呼吸）也停下。指针锁定时浏览器用 Esc 退出锁定，游戏把“游玩中丢失锁定”当作暂停；之后 400 毫秒内的 Esc 按键被忽略，避免暂停后马上又继续。
- 指针锁定请求失败（浏览器不支持、被拒绝、出错）时改用按住左键拖动转视角；方向键也能转视角。游玩中没有锁定时，点一下画面会重新请求锁定。游戏自己释放锁定（暂停、结束）和浏览器解除锁定（Esc）分开处理，暂停后马上继续不会被误判成又一次暂停。
- 视觉模型和物理胶囊分开：`CharacterView.root` 跟随胶囊脚底位置和朝向，模型挂在它下面的 `model-slot`。守卫用同款小人，换红黑配色。

### 规则

- 片段标识：稳定标识是“文件内容的 SHA-256 + 片段序号”；名字只用来显示（无名的显示为 `animation_<序号>`），同名片段靠序号区分。手动设置都按序号保存。
- 播放方式：读 `clip.userData.loop`。true / false 是明确值；缺失和非布尔值都算“未知”，按用途推断（待机、走、跑循环，其他只播一次），界面标“推断”。false 和缺失分开处理。跳的槽位总是只播一次。
- 用途识别：名字拆成词（按非字母数字分隔、拆开驼峰，不区分大小写）后按词首匹配英文关键词，中文按子串匹配。先看动作词（aim / fire / firing / shoot / reload / attack / punch / kick / hit / death / die / dance，以及瞄准、射击、开火、换弹、装弹、攻击、受击、死亡、跳舞），命中就归为“其他”；再依次看 jump / 跳 → run、sprint、jog / 奔跑、跑 → walk / 行走、走 → idle、stand / 待机、站立；都没有就是“其他”。
- 自动建议（每个动作槽位选一个）：
  1. 有手动把用途设为这一项的片段时，用其中序号最小的；
  2. 否则在“识别为这一用途、没有手动改成别的用途”的片段里选：待机、走、跑排除极短的片段和带位移（且没有锁定）的片段；优先 loop 明确为预期值的（待机、走、跑为 true，跳为 false），再按序号从小到大取第一个。其余候选在卡片上注明，可以手动选。
- 兜底：没有走用跑放慢（走速 / 跑速）；没有跑用走加快（跑速 / 走速）；没有待机用走（含由跑得到的走）的第一帧静止，也没有走就用绑定姿态；走和跑都没有（包括静态模型，以及只有节点动画、但用途都不是移动的模型）时提示“没有适用的移动动作，将使用整体摆动效果”，移动时让外层摆动节点里的模型整体上下晃动、向前倾。没有跳的片段时，跳跃中保持当前动作。
- 带位移的识别：
  1. 找片段里有 position 轨道、在层级里最靠上（离模型根最近）的节点；
  2. 能明确识别要同时满足：这一层只有一个这样的节点；它的父链（到模型根为止）在片段里没有旋转动画（也没有缩放动画，否则坐标系不确定）；父链到模型空间的静态变换可逆；
  3. 用轨道自己的插值器（与播放时一致）取这个节点的位置，换到模型空间，算相对第一个关键帧的水平（XZ）位移，最大值超过 0.2 m 就标为“带位移”。线性和阶跃插值只看关键帧（最大值一定在关键帧上）；CUBICSPLINE 在每个关键帧区间里再均匀取 31 个点，覆盖关键帧之间的运动。
- 锁定水平位移（每个片段单独勾选，只在能明确识别时提供）：生成一份片段副本，在模型空间里把这个节点每个关键帧的 X、Z 换成第一个关键帧的 X、Z，Y 保留；CUBICSPLINE 的切线去掉水平分量；其他所有轨道不变。原片段不改，取消勾选就用回原片段。不能识别时显示“该片段暂不支持锁定水平位移，请选择其他原地片段或使用兜底。”
- 归一化（只写外层节点）：包围盒按实际显示的顶点逐个计算（three 的 `getVertexPosition`：计入已经生效的 morph 权重，蒙皮网格再做蒙皮，含 bindMatrix / bindMatrixInverse 语义），实例化网格把每个 `instanceMatrix` 都算进去。带骨骼的模型按绑定姿态算（`src/import/bindPose.ts`）：绑定姿态由逆绑定矩阵（IBM）决定，文件里骨骼的初始姿态不一定是绑定姿态。导出工具对 IBM 的参照系有两种做法——场景空间（绑定姿态下蒙皮矩阵 K = 关节全局变换 · IBM = 单位矩阵，glTF 的本意）和骨架父节点空间（绑定姿态下 K = 根骨骼父节点的变换，three 的 `Skeleton.pose()` 默认这样理解；真实资产 armored-soldier 的 78 个关节在静止姿态下都满足这一种）——所以先看文件的静止姿态更符合哪一种：恰好是绑定姿态时其中一种的偏差为 0；都不符合时取偏差小的，相同时按 glTF 取场景空间。然后按这种参照系算出每根骨骼的绑定本地变换（普通父节点的变换正确补偿），在临时克隆上摆好再量，量完丢掉克隆。缩放到显示身高，最低点贴地，水平中心移到原点；绕 Y 轴按 90° 的倍数转。“没有待机也没有走”时的“绑定姿态”兜底用一个保持绑定姿态的片段（每根骨骼一组轨道），和其他动作一样淡入淡出。
- 无名节点的轨道：GLTFLoader 用模板节点的 UUID 指定无名节点的轨道目标，克隆后 UUID 会变。每个实例为这类片段生成一份把目标改成自己节点 UUID 的副本（`ModelInstance.clipFor`），原片段不改；所有目标节点都有名字时直接用原片段。实例的结构是：模型槽 → 摆动节点 → 外层节点（归一化）→ 克隆的模型。
- 资源：模板场景只用来克隆，不播放、不加入场景。实例释放时只释放自己的骨骼和 mixer 缓存；几何、材质、贴图由资产统一释放（卡片关闭且没有实例在用时）。

4. 要求 1：把“PLY 没有索引”当成点云；面上带 UV 或颜色时 PLYLoader 会生成没有索引的三角网格。现在按文件头里声明的面数判断是不是点云。
5. 要求 8：位移检测只看关键帧，漏掉 CUBICSPLINE 在关键帧之间的运动。现在用轨道自己的插值器在区间里取样。
6. 要求 11：拖动身高滑块时，每次变化都重建整张卡片，滑块被替换后拖动和键盘焦点丢失。现在卡片的控件只在打开时建一次，设置变化时只刷新文字、提示和片段表；片段表重建后把焦点还给同一个控件。

新增的测试：实例化网格的三角面数和超限拒绝、实例化网格的包围盒、网格节点有变换的单骨骼蒙皮（按实际蒙皮顶点贴地、居中、达到身高）、实例播放动画不改变包围盒、面上带 UV 的 PLY、只有点的 PLY（拒绝并释放）、OBJ 和 STL 校验失败时释放、CUBICSPLINE 关键帧之间的位移（标为带位移、不作为建议、锁定后为 0）；e2e 新增身高滑块的连续按键和连续拖动。把 normalize.ts、motion.ts、load.ts、importPanel.ts 分别换回 fe4e9dd 的版本时，对应的新测试都会失败。

### 第 2 轮审查后的修改

Codex 第 2 轮审查（候选 0ed5226）提出 4 项阻塞问题，都已修正：

1. 要求 12：无名骨骼的动画驱动不了克隆实例（轨道按模板节点的 UUID 指定目标，SkeletonUtils.clone 生成新 UUID）。现在每个实例为这类片段生成重定向的副本，原片段不改；预览和主角都走这条路径。
2. 要求 6：把文件里骨骼的初始姿态当作绑定姿态。现在在临时克隆上用 `Skeleton.pose()` 由逆绑定矩阵恢复绑定姿态再量；“绑定姿态”兜底也用它。
3. 要求 6：包围盒只读原始 POSITION，漏了已经生效的 morph 权重。现在用 three 的 `getVertexPosition`（先 morph，再蒙皮）。
4. 要求 3：加载后的异常路径没有释放资源。现在加载之后的所有步骤（统计、检查、包围盒、SHA-256、创建资产）都在同一个 try 里，失败时先释放；另外在加载后检查里拒绝“关节索引超出骨骼数量”的蒙皮（友好提示，不再在后面抛异常）。

修第 2 条时我先按“骨骼相对模型根 = 逆绑定矩阵的逆”写了一版，单元测试都通过，但真实资产组跑出 armored-soldier 的宽和深对调了（0.33 × 1.75 × 0.92）：它的逆绑定矩阵是相对骨架父节点的，而父节点有 −90° 的旋转和 1.75 倍的缩放。改为 three 自己的 `Skeleton.pose()` 约定后恢复为 0.92 × 1.75 × 0.33，并加了同样结构的合成测试。

新增的测试：无名骨骼的片段驱动两个克隆实例（互不影响、没有 No target node found 警告、原片段轨道名不变）；骨骼都有名字时直接用原片段；初始姿态不是绑定姿态（初始显示 3.5 m，播放回绑定姿态的 idle 后贴地、1.75 m）；没有片段时“绑定姿态”兜底；无骨骼和带骨骼的 morph；根骨骼挂在旋转、缩放的父节点下；关节索引越界的拒绝和释放；用 vi.mock 让加载后的步骤抛出意外异常，确认资源被释放。把 normalize.ts、pipeline.ts 换回 0ed5226 的版本、或让 clipFor 不做重定向时，对应的新测试都会失败。

### 第 3 轮审查后的修改

Codex 第 3 轮审查（候选 0bec204）提出 2 项阻塞问题，都已修正：

1. 要求 6：直接用 `Skeleton.pose()` 时，IBM 在场景空间、根骨骼的普通父节点带变换的文件会被重复应用父节点的变换（审查的例子：Armature 的 Y 缩放 2、IBM 的 Y 缩放 0.5，加载后高 1 m，却量出 2 m）。审查建议一律按场景空间换算根骨骼的绑定变换；但实测真实资产 armored-soldier 的 IBM 是骨架父节点空间（78 个关节静止姿态的 Σ‖K−P‖ ≈ 0.0001，Σ‖K−I‖ ≈ 230），一律按场景空间会把它转 90°、缩放 1.75 倍（第 2 轮时已经出现过宽深对调）。所以改为按文件的静止姿态判断参照系（见上面的“规则”），两种文件都正确。
2. 要求 12：切换到绑定姿态时立即停掉所有动作，没有淡出。现在绑定姿态是一个片段，和其他动作一样淡入淡出。

新增的测试：审查给出的“场景空间 IBM + 带缩放的普通父节点”（参照系判为场景空间，包围盒 1 m，播放保持原姿态的 idle 后显示 1.75 m 贴地）；参照系的三种判断；只有 jump 的骨骼落地后 0.001 秒仍接近 90°、过渡后回到 0°。把 normalize.ts 或 animator.ts 换回 0bec204 的版本时，对应的新测试失败。

### 已知问题和后续项

- P1 的 inspect 报告里 translation 通道的“水平位移”是在节点的父空间（本地坐标）里按首末关键帧算的，没有考虑父链的变换。armored-soldier 的 Hip 的父节点 BoneRoot 有较大的静态旋转，所以本地 XZ 不是水平面：P1 报告“移动类片段里 Hip 的水平位移几乎为 0”，而 P3 按模型空间计算，X Bot@Rifle Run 实际带约 2.0 m 的水平位移。建议后续把 P1 的报告改为模型空间，或注明是本地坐标。
- STL / PLY 常见 Z 轴向上，本版只支持绕 Y 轴转 90°，没有转换上轴。
- 导入的设置（身高、旋转、用途、播放方式、锁定）只在内存里，刷新后丢失（任务要求如此）；以后需要持久化时按“SHA-256 + 序号”保存。
- GLTFLoader 解析和贴图解码在主线程，大文件会让页面短暂卡顿（承诺范围之外）。
- P1 的 inspect 报告也没有考虑 EXT_mesh_gpu_instancing（三角面数和包围盒按单个实例算）、morph 和蒙皮对网格节点变换的抵消；P3 的导入检查以加载后的实际结果为准。
- IBM 的参照系按文件的静止姿态判断。如果一个文件的静止姿态不是绑定姿态，而且偏离得比根骨骼父节点的变换还大，可能判断错参照系；两个真实资产和审查给出的合成文件都判断正确。
