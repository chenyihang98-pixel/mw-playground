### 第 1 轮审查后的修改

Codex 第 1 轮审查（候选 abf8088）提出 3 项阻塞问题，都已修正（违反的都是要求 5）：

1. 容器损坏被当作检查成功：重复的 JSON 块、重复的 BIN 块、未按 4 字节对齐的块只记在“问题”里，退出码 0。现在凡是检查到的容器损坏都返回错误（退出码 1）：块长度不是 4 的倍数、重复的 JSON 块、重复或不在第二位的 BIN 块、头部声明长度小于实际长度（尾部多余字节）、BIN 块比 buffers[0].byteLength 短或长出 3 字节以上、buffers[0] 指向 BIN 块但没有 BIN 块。顺带把 JSON 块的 BOM、0 字节补齐，以及缺 asset / asset.version、版本不是 2.x 也改为错误（three r187 的 GLTFLoader 在缺 asset.version 时会直接出错）。规范允许的未知类型块仍只记在“问题”里。
2. 访问器按未经验证的 count 分配数组：count 为 2**50 时抛 RangeError，被当作内部错误。现在先按 JSON 声明的 bufferView / buffer 长度检查访问区间（外部 buffer 也能检查），再读数据；读取改成按需逐个读取，不再按 count 分配数组；没有 bufferView 的全零访问器只检查一个元素。三角面数用到的 count 也先经过同样的检查。
3. FLOAT 分量的 NaN / Infinity 没有检查：包围盒在 JSON 里变成 null 但仍标为已计算。现在读取时逐个检查有限性，受影响的指标（实际包围盒、实际时长、水平位移）写“未计算”和原因，并在“问题”里记一条；包围盒和位移的计算结果也检查是否溢出。

另外修了一处同类问题：动画时长原来用 `Math.max(...列表)`，通道数很多时（实测 30 万个）会超出调用栈而抛异常。

### 设计说明

- 碰撞是 2.5D 的：胶囊在 XZ 平面上是圆，盒子、高台、坡道是 XZ 矩形加顶面高度。脚底高度为 y 时，顶面高于 y + 余量的部分是墙（着地时余量 = 迈步高度，空中为 0）；坡道的顶面是线性的，高于某个高度的部分仍是一个矩形。坡道只有两个侧面是墙：圆心在坡道的横向范围内时坡道不挡（斜坡顶面是地面，不是墙）；圆心在坡道上时，所贴的高台在坡道高端那一侧也不挡。这两条判断用每一小段移动开始时的圆心，所以从侧面靠近时仍会先被侧面挡住。圆被推出墙时只去掉法向分量，所以能沿墙滑动；位移按半个半径分段，挤不进比直径窄的缝时停在原处。地图边界直接限制圆心。
- 支撑高度取圆心所在位置的最高顶面；走出高台边缘时圆心离开顶面就开始下落。
- 守卫沿路线（最后一点回到第一点）匀速循环，只在地面上走，不受玩家影响；关卡校验要求路线离所有实体至少一个胶囊半径。守卫与玩家的胶囊水平距离小于两个半径、竖直范围重叠就算接触。
- 胜负在同一步里先判收集再判时间；分出胜负、暂停、未开始时 `stepGame` 原样返回。重开就是重新生成关卡的初始状态（`restartGame` 的结果与 `createInitialState` 相等），界面上随后直接开始。
- 暂停时 `advance` 不推进并丢弃累计时间（继续时不会补上暂停期间的时间），同时释放指针锁定；连装饰性的动画（宝石旋转、待机呼吸）也停下。指针锁定时浏览器用 Esc 退出锁定，游戏把“游玩中丢失锁定”当作暂停；之后 400 毫秒内的 Esc 按键被忽略，避免暂停后马上又继续。
- 指针锁定请求失败（浏览器不支持、被拒绝、出错）时改用按住左键拖动转视角；方向键也能转视角。游玩中没有锁定时，点一下画面会重新请求锁定。游戏自己释放锁定（暂停、结束）和浏览器解除锁定（Esc）分开处理，暂停后马上继续不会被误判成又一次暂停。
- 视觉模型和物理胶囊分开：`CharacterView.root` 跟随胶囊脚底位置和朝向，模型挂在它下面的 `model-slot`。守卫用同款小人，换红黑配色。

### 规则

- 片段标识：稳定标识是“文件内容的 SHA-256 + 片段序号”；名字只用来显示（无名的显示为 `animation_<序号>`），同名片段靠序号区分。手动设置都按序号保存。
- 播放方式：读 `clip.userData.loop`。true / false 是明确值；缺失和非布尔值都算“未知”，按用途推断（待机、走、跑循环，其他只播一次），界面标“推断”。false 和缺失分开处理。跳的槽位总是只播一次。
- 用途识别：名字拆成词（按非字母数字分隔、拆开驼峰，不区分大小写）后按词首匹配英文关键词，中文按子串匹配。先看动作词（aim / fire / firing / shoot / reload / attack / punch / kick / hit / death / die / dance，以及瞄准、射击、开火、换弹、装弹、攻击、受击、死亡、跳舞），命中就归为“其他”；再依次看 jump / 跳 → run、sprint、jog / 奔跑、跑 → walk / 行走、走 → idle、stand / 待机、站立；都没有就是“其他”。
- 自动建议（每个动作槽位选一个）：
  1. 有手动把用途设为这一项的片段时，用其中序号最小的；
  2. 否则在“识别为这一用途、没有手动改成别的用途”的片段里选：待机、走、跑排除极短的片段和带位移（且没有锁定）的片段；优先 loop 明确为预期值的（待机、走、跑为 true，跳为 false），再按序号从小到大取第一个。其余候选在卡片上注明，可以手动选。
- 兜底：没有走用跑放慢（走速 / 跑速）；没有跑用走加快（跑速 / 走速）；没有待机用走（含由跑得到的走）的第一帧静止，也没有走就用绑定姿态；走和跑都没有（包括静态模型，以及只有节点动画、但用途都不是移动的模型）时提示“没有适用的移动动作，将使用整体摆动效果”，移动时让外层摆动节点里的模型整体上下晃动、向前倾。没有跳的片段时，跳跃中保持当前动作。
- 带位移的识别：
  1. 找片段里有 position 轨道、在层级里最靠上（离模型根最近）的节点；
  2. 能明确识别要同时满足：这一层只有一个这样的节点；它的父链（到模型根为止）在片段里没有旋转动画（也没有缩放动画，否则坐标系不确定）；父链到模型空间的静态变换可逆；
  3. 用轨道自己的插值器（与播放时一致）取这个节点的位置，换到模型空间，算相对第一个关键帧的水平（XZ）位移，最大值超过 0.2 m 就标为“带位移”。线性和阶跃插值只看关键帧（最大值一定在关键帧上）；CUBICSPLINE 在每个关键帧区间里再均匀取 31 个点，覆盖关键帧之间的运动。
- 锁定水平位移（每个片段单独勾选，只在能明确识别时提供）：生成一份片段副本，在模型空间里把这个节点每个关键帧的 X、Z 换成第一个关键帧的 X、Z，Y 保留；CUBICSPLINE 的切线去掉水平分量；其他所有轨道不变。原片段不改，取消勾选就用回原片段。不能识别时显示“该片段暂不支持锁定水平位移，请选择其他原地片段或使用兜底。”
- 归一化（只写外层节点）：包围盒按实际显示的顶点逐个计算（three 的 `getVertexPosition`：计入已经生效的 morph 权重，蒙皮网格再做蒙皮，含 bindMatrix / bindMatrixInverse 语义），实例化网格把每个 `instanceMatrix` 都算进去。带骨骼的模型按绑定姿态算（`src/import/bindPose.ts`）：绑定姿态由逆绑定矩阵（IBM）决定，文件里骨骼的初始姿态不一定是绑定姿态。three 显示蒙皮网格的方式与 glTF 规范一致（GLTFLoader 以单位矩阵绑定，attached 模式抵消网格节点自己的变换）：显示的顶点 = Σ w · K · v，K = 关节全局变换 · IBM。默认按 glTF 规范的场景空间：绑定姿态下 K = 单位矩阵，网格按原始顶点显示。兼容一种特殊导出：整个模型（蒙皮网格和骨架）被一起套进带变换的节点、IBM 没有跟着更新——真实资产 armored-soldier 就是这样，导出工具在原模型外面套了 −90° 旋转和 1.75 倍缩放两层节点，蒙皮网格和根骨骼都在里面。这时按网格节点空间理解（绑定姿态下 K = 蒙皮网格节点的全局变换 M）。只看文件的静态结构，同时满足才算：所有蒙皮网格节点的全局变换相同（M），M 不是单位矩阵、可逆，网格节点的父链里没有骨骼；每条骨骼链所在的普通父节点的全局变换也等于 M；文件里每个关节的静止姿态都正好满足 K = M（容差 1e-3，平移按骨骼分布的尺度换算；armored-soldier 的最大偏差约 5e-6）。其余一律按场景空间。判断与片段无关，增加、删除或修改动作都不会改变对同一套 IBM 的理解。然后按这种参照系算出每根骨骼的绑定本地变换（普通父节点的变换正确补偿），在临时克隆上摆好再量，量完丢掉克隆。绑定姿态在导入时只算一次，包围盒、“绑定姿态”片段和实例都用同一份。缩放到显示身高，最低点贴地，水平中心移到原点；绕 Y 轴按 90° 的倍数转。“没有待机也没有走”时的“绑定姿态”兜底用一个保持绑定姿态的片段（每根骨骼一组轨道），和其他动作一样淡入淡出；它的轨道路径和 GLTFLoader 给文件片段用的一致（有名字的骨骼用名字，无名骨骼用 UUID），three 按轨道路径给每个属性建一份混合状态，路径一致才能在同一份状态里交叉淡入淡出。
- 无名节点的轨道：GLTFLoader 用模板节点的 UUID 指定无名节点的轨道目标，克隆后 UUID 会变。每个实例为这类片段生成一份把目标改成自己节点 UUID 的副本（`ModelInstance.clipFor`），原片段不改；所有目标节点都有名字时直接用原片段。实例的结构是：模型槽 → 摆动节点 → 外层节点（归一化）→ 克隆的模型。
- 资源：模板场景只用来克隆，不播放、不加入场景。实例释放时只释放自己的骨骼和 mixer 缓存；几何、材质、贴图由资产统一释放（卡片关闭且没有实例在用时）。

### 存储格式和版本号

IndexedDB 数据库 `mw-playground`（数据库版本 1），对象仓库 `roster`，每个人物一条记录，键是文件内容的 SHA-256。记录（格式版本 1）：

| 字段 | 内容 |
|---|---|
| `format` | 固定为 `mw-roster-person` |
| `version` | 存储格式的版本号，现在是 1 |
| `id`、`sha256` | 文件内容的 SHA-256（十六进制，两者相同，也等于存储的键） |
| `fileName` | 原文件名 |
| `displayName` | 显示名（默认是文件名，最长 60 个字符） |
| `order` | 加入的先后（名册列表、守卫分配都按它排） |
| `role` | 分工：`player` 主角、`guard` 守卫、`playerGuard` 主角兼守卫、`companion` 同伴、`none` 不出场 |
| `settings.displayHeight` | 显示身高（米） |
| `settings.quarterTurns` | 绕 Y 轴转了几个 90°（0–3） |
| `settings.purposes` | 片段用途的手动选择，键是“SHA-256#片段序号” |
| `settings.playbacks` | 播放方式的手动选择（`loop` / `once`），键同上 |
| `settings.lockedMotion` | 勾选了锁定水平位移的片段（“SHA-256#片段序号”） |
| `file` | 原文件内容（Blob） |

- 只保存原文件和设置，不保存加载后的对象或归一化结果。
- 读出的每条记录都用 zod 校验。以下情况都不抛异常，提示后跳过那一项：
  - 版本号不是 1；
  - 格式名不对、字段缺失或类型不对；
  - 键和 id 不一致；
  - 片段键不属于这个文件。
- 跳过的项仍在名册里标为失败，只能删除，不会被覆盖。

### 恢复流程

1. 页面加载时读出所有记录。读不了（浏览器禁止、出错）时给出存储失败的提示，名册从空开始，游戏照常。
2. 校验每条记录（见上）。合格的按 `order` 排序，逐个处理：
   1. 把保存的文件内容交给 `importModel`，和导入新文件走同一条流程（类型、读取、预检、解析、加载后检查、归一化）。
   2. 新加载的资产的 SHA-256 必须等于记录里的值。
   3. 套上保存的设置：身高、转向、用途、播放方式、锁定。序号超出片段数或不能锁定的项忽略。
3. 某一项被拒绝或解析失败时，给出提示（“……恢复失败：原因，已跳过”），名册里标为失败，记录保留，可以删除；其余照常恢复。
4. 每恢复完一项就重新分配出场的人物。同一个文件和同样的设置，恢复后的尺寸、朝向、片段建议和手动设置与加入时一致（单元测试逐项比较；真实资产组也比较了尺寸和朝向）。
5. 加入名册之后，资产上的设置一变就保存。同一条记录的写入按顺序进行，失败时给出提示，不抛异常。

### 分工和分配规则（`src/roster/cast.ts`）

- 五种分工：主角；守卫；主角兼守卫；同伴；不出场。新加入的人物分工为“不出场”。
- 主角（含主角兼守卫）最多一个。设新主角或点“恢复默认主角”时，原来的主角（包括主角兼守卫）改为“不出场”。没有主角时用默认小人。
- 同伴最多 3 个（`ROSTER_LIMITS.maxCompanions`）：第 4 个设不上，给出提示。
- 守卫只替换关卡里守卫的外观，数量和路线不变：
  - 分工为守卫或主角兼守卫的人物按名册顺序（加入的先后），依次分给关卡数据里按顺序排列的守卫。
  - 人物不够时，剩下的守卫用默认小人。
  - 人物多出来时，多出的不出场，并提示“关卡里只有 N 个守卫：…… 不出场”。
- 主角兼守卫：主角和守卫的位置上各有一个独立的实例，两个实例的骨骼和 AnimationMixer 各自独立。
- 同屏实例上限沿用 P3 的 12（`IMPORT_LIMITS.instancesMax`）：
  - 按主角 → 守卫 → 同伴的顺序占用，主角兼守卫占两个。
  - 超出时，多出的守卫或同伴不出场，并提示。
- 恢复失败的人物不出场，并提示。
- 名册最多 20 个人物（`ROSTER_LIMITS.maxPeople`，包括恢复失败、仍留在存储里的项）。到了上限不能再加入，给出提示。
- 同一个文件（SHA-256 相同）再次加入时不新增，提示“已在名册里”，并在名册里标出那一项。“设为主角”遇到这种情况时，把名册里的那一项设为主角。
- 删除正在使用的人物：
  - 先从名册移除并重新分配：主角换回默认主角，守卫换回默认小人，同伴从场景和模拟里移除。
  - 再释放它的实例和资源（按 P3 的释放规则），最后从存储里删除。导入卡片上正打开着它时，一起关掉。
- 导入失败时，名册、分配和当前主角都不变。

### 同伴的参数（`SPEC.companion`）

| 参数 | 取值 | 说明 |
|---|---|---|
| 跟随距离 | 1.8 m | 目标点在主角身后这么远 |
| 左右间距 | 1.1 m | 多个同伴的目标点以主角身后为中心左右错开 |
| 停下距离 | 0.3 m | 离目标点不超过它就停下 |
| 重新起步距离 | 0.8 m | 停下后离目标点超过它才起步（避免抖动） |
| 跑步距离 | 4 m | 离目标点超过它用跑步速度（5 m/s），否则用走路速度（2.2 m/s） |
| 卡住距离 | 8 m | 离主角超过它…… |
| 卡住时长 | 3 s | ……并持续这么久，就传送到主角附近 |
| 重试间隔 | 0.5 s | 找不到可以传送的位置时，隔这么久再试 |
| 找位置的间距、圈数、方向数 | 1.8 m、3 圈、16 个 | 开局和传送时，先试这个同伴的跟随目标点，再在主角周围 1.8 / 3.6 / 5.4 m 的圈上，从身后开始左右交替找 |

`specProblems()` 增加了三条约束：

- 重新起步距离大于停下距离；
- 找位置的最大范围小于卡住距离；
- 跟随位置离主角的距离小于卡住距离。

### 同伴的设计说明

- 移动写在固定步长的纯模拟里，和主角用同一个 `stepPlayer`：同样的速度、迈步、坡道、重力、从边缘掉落、地图碰撞（障碍、高台侧面、边界）。同伴的输入是“朝目标点走”：
  - 方向指向目标点；离目标点远时跑，近时走；
  - 最后一小段按剩下的距离减速，正好停在目标点上；
  - 同伴不跳。
- 同伴和主角、其他同伴、守卫之间不做碰撞，可以重叠，所以不会推挡主角（单元测试：有同伴和没有同伴时，主角的每一步都完全相同）。
- 收集和守卫扣时只看主角，同伴不影响胜负；守卫的移动也不受同伴影响。
- 渲染层只读同伴的状态。
- 暂停、未开始、分出胜负时 `stepGame` 原样返回，同伴也停下。重开时同伴回到开局的位置。
- “能站的位置”同时满足：
  - 胶囊在地图内；
  - 脚下表面的高度和主角脚下表面相差不超过迈步高度；
  - 胶囊不和会挡住它的实体重叠（按迈步余量 0 判断，比移动时更严）。

  开局时找不到这样的位置，就和主角站在一起（可以重叠）；传送时找不到，就留在原地，隔 0.5 s 再试。
- 分工变化时同步模拟里的同伴（`setCompanions`）：
  - 还没开始时，所有同伴回到开局位置；
  - 否则已有的保留状态，新加入的出现在主角附近，移除的消失。
- 同伴是导入人物时，用 P3 的动画驱动按它自己的移动状态切换片段；静态模型用 P3 的整体摆动。

### 存储失败

- 以下情况都给出提示（名册面板顶部的红色提示，以及快照里的 `roster.storage.problem`）：
  - IndexedDB 打不开（浏览器不支持、被禁止）；
  - 配额不够（提示“存储空间不够”）；
  - 读写抛错、事务中止。
- 游戏照常运行，当前会话里的名册照常能用，只是不保存。之后某次保存成功时清掉提示。

### 已知问题和后续项

- 同伴直接朝目标点走，没有寻路：被障碍挡住时沿墙滑动，走不过去就停在墙边，持续离主角太远时靠传送解决。
- 名册恢复是逐个进行的。大文件多时，页面加载后要等一会儿才全部出场；恢复期间可以照常游玩，恢复完的人物随时换上。
- 恢复还没完成时又加入了新人物，新人物的 `order` 可能和存储里的记录相同。名册列表仍按加入的先后显示，刷新后相同 `order` 的几项按存储的键排序。
- P3 已知问题里“导入的设置只在内存里，刷新后丢失”：加入名册的人物现在会保存；只导入、没加入名册的仍然只在内存里。
